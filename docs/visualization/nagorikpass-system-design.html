A visitor expected on a later date can still be checked in, because the PRD sets no restriction. Every assignment and return stays in card history.

Cards are reusable. The card is linked to this visit only. After a confirmed return it is Available, and the Receptionist can issue it to the next visitor. The card number is never the visitor’s ID: the Visitor ID (visitors.visitor_code) is assigned by hand by HR/Admin, once (OQ-1).

One active visit per phone (OQ-10). A phone number with an expected or checked_in visit can’t be registered again until that visit ends (visitor_has_active_visit).

Google sign-in: choose an outcome

Decided: OQ-11 Google Sign-In accepts only the company Google Workspace domain. /auth/callback checks the verified email on the server; Google’s hd hint only narrows the account picker. Passing the check doesn’t replace authorization. Pending: domain value COMPANY_EMAIL_DOMAIN is a placeholder until the owner provides it, and Google can’t be enabled until then. Decided: OQ-12 Only company email addresses are used for invitations and sign-in; a personal email can’t be linked to an employee account. Unverified assumption: TC-AUTH-10 Google links to an invited account with the same user ID. Phase 1 must verify this. If it differs, Google must be limited to accepted invitations.

    Google Cloud, Supabase and other external configuration still required
    • Google Cloud: consent screen (the Internal user type fits when the project belongs to the company Workspace; the server-side domain check applies either way), a Web OAuth client, scopes openid, email and profile, and redirect URI https://<project-ref>.supabase.co/auth/v1/callback.
    • Supabase: enable Google, set the Site URL, and allow /auth/callback and /auth/confirm.
    • Public sign-up must be off before Google is enabled. It was on for the hosted project at the last check.
    • Set COMPANY_EMAIL_DOMAIN in the server environment. Google can’t be enabled until the owner provides the domain.
    • Telegram: bot token and the HR/Admin chat ID, when the owner implements it (OQ-4). No webhook.
    • Email: a production email service for invitations. Provider pending (OQ-13).
    • Vercel: the daily No-Show job works on any plan; the notification retry schedule depends on the plan, which is pending (OQ-14).
    Rollback
    • Application: promote the previous Vercel deployment.
    • Database: a forward fix or the written backout. Restore from backup only as a last resort.
    • Google: disable the provider in Supabase. Email and password keep working.
    • Notifications: no rollback needed; the manual fallback applies, and calls aren’t recorded (OQ-9).
